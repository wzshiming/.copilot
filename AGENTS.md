# AGENTS.md

Personal agents repository — agent definitions plus the scripts they run, no application code.

## Structure

Only `.github/`, `agents/`, `hooks/`, `scripts/`, `tests/`, dotfiles, root Markdown docs, `LICENSE`, and `Makefile` are tracked; everything else at the root is local runtime state excluded by the `.gitignore` whitelist.

### Scripts

- Each script lives in `scripts/<name>.sh` as POSIX sh (`#!/bin/sh`, clean under `shellcheck -s sh`), called as `~/.copilot/scripts/<name>.sh [-C <repo-path>] <args>`; the lock block `take_lock` is identical in `scripts/worktree-add.sh` and `scripts/worktree-remove.sh` and is edited in both together.
- A script never prompts, reads no environment variable as configuration, and never forces; an unmet precondition makes it refuse and say why.
- Exit codes: `0` done, `1` refused or failed, `2` usage error; a script's `--help` may define more (`ci-wait.sh`: `3` still pending at the deadline); results print as `key=value` lines, a listing (`worktree-status.sh`) as one line per item, a watcher as one progress line per poll plus the final table; `--help` prints one paragraph.
- Tests live in `tests/<name>.bats` (bats-core); reusable fake commands live in `tests/mock/<cmd>`, never as stubs written inside a single `.bats` file.

### Hooks

- Each hook lives in `hooks/<event>.sh` as POSIX sh (`#!/bin/sh`, executable, clean under `shellcheck -s sh`, no node, jq, or network), shares `hooks/lib.sh`, reads the harness's JSON event on stdin, composes this checkout's `scripts/` (`../scripts/` relative to itself), and is tested in `tests/<event>.bats`.
- A hook is registered only in the `hooks:` frontmatter of the agent whose lifecycle it manages — the Coder: `SubagentStart` creates `.worktrees/coder/<agent-id>` on branch `coder/<agent-id>` from the main checkout's HEAD and injects worktree, branch, base_sha, and main_root into the Coder; `SubagentStop` blocks once on a dirty tree so the Coder commits or discards, then removes the worktree (a tree still dirty at the second stop stays for the cleanup intent) and keeps the branch (one whose tip HEAD already contains is deleted); both hooks also run `worktree-remove.sh --orphans`, because VS Code's Keep re-saves a Coder's accepted edits into its removed worktree path as plain files, which the sweep deletes once every file is a blob the repository has; a Stop that never fires (cancelled or dead dispatch) leaves both for the resume's Executor inventory and the cleanup intent, nothing automatic.
- An entry carries no `cwd` — the harness runs a hook via `/bin/sh -c` in the entry's `cwd`, defaulting to the workspace's first folder, and overwrites the event's `cwd` with it, so a fixed one would pin every Coder to one repository — and no `timeout`, which the frontmatter parser drops (a scalar arrives as a string), leaving the 30 s default; the hooks thus assume a single-root workspace whose folder is the target repository, and a multi-root workspace or another root gives the Coder `no worktree: <reason>` and it stops.
- Frontmatter hooks of a user-level agent file run only with `chat.useHooks` (default on) in a trusted workspace, for the agent whose frontmatter names them, never its dispatcher; agent files are read from the main checkout's `~/.copilot/agents/`, so a hook change takes effect once that checkout carries it.

### Agents

- Each agent lives in `agents/<name>.agent.md` with YAML frontmatter. Every agent has `name`, `description`, `argument-hint`, `model` (fallback list), and `agents` (dispatchable subagents); `tools`, `user-invocable`, `disable-model-invocation`, `handoffs`, and `hooks` are used where applicable.
- `handoffs` link user-invocable agents along meaningful transitions only and are all manual — never set `send: true`: Autopilot auto-fires the first `send` handoff after every response and can loop agents. Prompts are inserted verbatim (no `${…}` substitution) into the same session, so they name only what is handed over plus facts the target cannot see (e.g. ledger paths); the target agent's body supplies the method.
- Challenger and Reviewer share one verbatim `## Constraints` block and the quoted fit question; Coder, Orchestrator, and that block share the Executor-dispatch sentence; Scout and Executor share the auto-approval bullet; Planner and Detailer share the Modules rule; Planner, Orchestrator, and Challenger share the Language rule and the Parallel dispatch rule — there is no include mechanism, so edit every copy together.

## Checks

- `make check` — Prettier format check + markdownlint + shellcheck + bats, the full suite.
- `make lint` — markdownlint on Markdown + `shellcheck -s sh` on `scripts/*.sh` and `hooks/*.sh`.
- `make test` — bats-core on `tests/*.bats`.
- `make format` — Prettier rewrites Markdown.
- These targets, or the commands they run on specific files, may run locally without asking.
- CI (`.github/workflows/ci.yml`) runs `make check` on `ubuntu-latest` and `macos-latest` for pushes to `master` and all PRs.

## Conventions

- Agents orchestrate, Executor executes: an agent body holds its flow plus only the knowledge its role needs (Planner and Detailer design by the Modules rule; Orchestrator orchestrates; Coder implements under its test and refactoring disciplines; Reviewer and Challenger review; Executor and Scout run commands by their own conventions); the git/gh workflow lives only in Executor's Rules and, for a Coder's worktree lifecycle, in `hooks/`, and each fixed multi-command flow is a script in `scripts/` that Executor names at the rule needing it or a hook calls; dispatchers (Orchestrator, Coder, Reviewer, Challenger) ask for a git/gh step by its intent alone — commit, join a pair, land, wait on CI, read a baseline, clean up, open an Issue — never by a command form, another document, or a description of its mechanics, the exceptions being Coder's exact `git add <paths>` and `git commit` commands for its own files (its Commit step), its one `git reset --hard <start ref>` (its Start step), and the `git restore`/`rm` that discard its own leftovers; Coder keeps a one-line restatement of its hook-worktree constraint and Scout and Executor of the dispatched-path constraint, as a subagent is stateless and receives only its body and brief; no body restates the harness base prompt.
- Agent bodies open with one sentence in normal case, `You are the <role>: <mission>.` — no shouted words.
- Agent body sections are H2 only, one per name, in this order and only when needed: Input, Constraints, Approach (a subagent's checklist) or Workflow (the Orchestrator's and Planner's phase loop), Rules, Output Format.
- List items are fragments or single sentences without a terminal period — split an item rather than write two sentences in it; only Workflow phase items are paragraphs with a bold `**Phase**:` label and full punctuation, every other label is plain `Label:`.
- Emphasis: `_Agent_` italics for agent names, bold only for Workflow phase names — their labels and references back to them — and a body's key-fact line (`**Ledger**`, `**Current plan**`), backticks for paths and commands, `#tool:` for tools; a list's lead-in sentence ends with a colon.
- Model-invocable agents (no `disable-model-invocation: true`) carry concrete "Use when:" trigger phrases in `description` — that is the discovery surface. Every `description` is at most 35 words, shorter preferred: one outcome clause (what it does, not its steps), then `Use when:` with up to three triggers specific to the task rather than universal ones. Keep model names out of descriptions; they live in `model:` and the body. A dispatch-only agent's description names no dispatcher or dispatchee; a user-invocable agent's may name the agents whose handoffs feed it.
- Keep shell snippets auto-approvable and self-contained: a fixed flow is one script call, approvable whole; any other command has no `export …;` preamble or `VAR=… cmd` prefix and no zsh-only syntax, with shell variables only in steps that need approval anyway. Guards are flags, not environment: `-m`/`-F` and `--no-edit`/`--ff-only` instead of `GIT_EDITOR`, `-c core.editor=true rebase --continue`, `git --no-pager`, a flag for every value `gh` would prompt for, and a pipe (`| cat` or a filter) on `gh` output (it pages whenever the shell sets `PAGER`), watchers included rather than redirected (a redirect leaves an agent terminal silent, and 5 silent minutes move it to the background). Credential prompts need no guard: agent terminals carry VS Code's `GIT_ASKPASS` or `GIT_TERMINAL_PROMPT=0`.
- Testing policy across agents and scripts: the full suite runs on CI and local runs stay targeted — the baseline from the start commit's CI run, else one local run (Executor's CI rule); tests for the change while implementing (Coder — the tests half's fail-first tests, the implementation half's and a single stage's touched tests); no full-suite requirement per commit (Coder's Commit step); every push to a PR branch runs the full suite on CI as the merge gate, its result awaited by Executor within a default deadline, unreachable CI falling back to one local full run (Executor's CI rule and `scripts/ci-wait.sh`); one local full run on the exact tree only before a landing that goes to no PR (Executor's Landing rule); review gates read the reviewed commit's CI result (Reviewer, Challenger).
- Execution policy across agents: only Scout (side-effect-free reads) and Executor run terminal commands, each naming its `execute/<tool>` entries instead of the `execute` set, which also carries VS Code's built-in execution subagent; Coder, Orchestrator, Reviewer, and Challenger dispatch Executor by its `argument-hint` — the repository or worktree path, the goal or exact commands or a git/gh intent with its facts (commit, join, landing, CI wait, baseline, cleanup, Issue), and what to report — one dispatch per step; Executor derives a goal's commands from the repo's documented tooling and runs destructive commands only when named; the dispatcher's own constraints govern what it may ask for.
- Implementation policy across agents: the Orchestrator classifies each stage — a behavior stage as a tests/implementation pair, any other as one Coder — and records its contract (the module's detail) and file split in the ledger before dispatch; a Coder's hooks create and remove its worktree, so its part exists only as a branch (the Hooks subsection, Coder's hook-worktree constraint), and Executor joins, lands, and cleans up by branch, materializing a working tree only inside one dispatch (Executor's Materialize, Join, and Landing rules with `scripts/worktree-*.sh`); two branches are combined only by rebase and fast-forward, never a merge commit: the join rebases the tests branch onto the implementation branch, so the joined branch is the tests branch and the implementation branch is deleted at a green join, a red or conflicting join leaving both as reported, and a landing rebases onto its base and fast-forwards (Executor's Join and Landing rules); the halves run in parallel, each holding only its own worktree and part; the Orchestrator reads, edits, and runs nothing itself; Coder is dispatch-only (`user-invocable: false`, no handoffs) and commits its verified part through Executor; the Orchestrator body is the single home of stage classification and join attribution, the Coder body of the halves' discipline (the Iron Law in pair form, good tests) and the refactoring discipline (single-stage refactorings, the joined-branch cleanup pass).
- Review policy across agents: the review requirement — review gates as the Orchestrator schedules them (the default), one review gate before landing only, or none (no gate, the Orchestrator's per-stage verification from Executor and Scout evidence being what remains) — is the user's choice, asked for by the Planner at Alignment in every run and by the Orchestrator at Intake only when no plan carries one, with none recommended for an early-stage project and the scheduled gates otherwise, an unavailable user meaning the default, recorded as an assumption; the Orchestrator schedules review gates at Intake in every run, within it (more review than it allows is a question to the user, never a silently added gate), and judges the stages between them from Executor and Scout evidence; Reviewer runs at the gates, not after every stage; Challenger runs only when the user asks (in chat or as a plan decision) or a gate fails three Reviewer rounds; the Reviewer is the one review body (the necessity audit and correctness attack live in it), and the Challenger cross-examines through three Reviewer dispatches pinned to other models, confirming an issue by two-of-three agreement or its own evidence.
- Design policy across agents: Planner and Detailer design from the whole, by criteria that live only in the Modules rule (a change designed in rather than patched on, compatibility layers only for an explicit recorded requirement, reuse before build) and reach the plan as decisions and acceptance criteria; the Orchestrator decomposes the design; Coder implements the contract, reporting rather than writing a patch or restructuring the plan did not foresee; Reviewer and Challenger ask the fit question, "does this fit the plan's design or patch around it?", against those decisions and criteria.
- Planning policy across agents: work is planned in two layers — the Planner's Outline (modules with contracts and dependencies, waves, decisions — the only plan format, one module or many), approved by the user, then the Orchestrator's Detailers of a wave together in one tool-call block, each detailing its module at the functional level inside its contract, a wave being every module that needs no code still unlanded; the Planner's and the Detailer's Output Formats are the Outline's and the Module Detail's single home; the plan states what the change is and must satisfy, never how (the Planner's Plan boundary rule); its decisions carry the landing requirement, the review requirement, sourced compatibility requirements, and any requested Challenger pass; the Orchestrator records each Module Detail in its ledger as the stage contract, derives stages, gates, and landing from it, orders a wave's stages by the modules' declared dependencies, details the next wave at its checkpoint, puts to the user only the details' Open questions, never the details themselves, and returns to the Planner through Re-plan only for a re-cut, a contract change, invalidated assumptions, or a scope change; the Orchestrator alone lists Detailer in `agents`, and Detailer dispatches only Scout.
- Dispatch interface across agents: `argument-hint` is the single home of what a dispatch must carry (a dispatcher sees only name, description, and hint); `## Input` restates it with semantics and adds nothing; a dispatcher's brief adds only what the hint cannot know — the overall goal, the stage or gate scope, prior outputs, the plan's decisions that bind the work, its own recorded verification results — and never describes the target's method; the Orchestrator's `Stage dispatches:` rule is the policy's home in a body and the Challenger's shared prompt embodies it; no body describes another agent's mechanics, the shared blocks of the Agents subsection and Executor's intent list being the only cross-agent text.
- Dispatch policy across agents: subagent dispatches needing none of one another's results or side effects form one batch issued in one tool-call block, because the harness runs concurrently only the calls of one block and a dispatch issued after another has returned runs alone; each body names its batches — Planner's Discovery Scouts, the Orchestrator's Intake Scouts, the Detailers of a wave, the two halves of a pair, and singles with no declared dependency and disjoint files, Challenger's three pinned Reviewer dispatches — and the rule's single home is the shared `Parallel dispatch:` Rules bullet of the three user-invocable agents (Planner, Orchestrator, Challenger); the harness base prompt asks only generically for independent calls in one block, and the rule adds what counts as a batch here and that a later dispatch runs alone, so it restates nothing from the base prompt.
- Language policy across agents: the user-invocable agents (Planner, Orchestrator, Challenger) share one `Language:` rule — replies and questions (options included) are in the language the user writes in, read from the user's own messages and never from a handoff prompt — and nothing else (dispatch briefs, subagent reports, memory files) is bound to it, so the dispatch-only agents carry no rule of their own, while commits, issues, and PR text keep the project's language (Coder's Commit step and Executor's PR and Issue rules); the harness adds a locale instruction only for a non-English VS Code display language or `github.copilot.chat.localeOverride`, so the rule restates nothing from the base prompt.
