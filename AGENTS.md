# AGENTS.md

Personal agent and skills repository — Markdown docs only, no application code.

## Structure

Only `.github/`, `skills/`, `agents/`, dotfiles, root Markdown docs, `LICENSE`, and `Makefile` are tracked; everything else at the root is local runtime state excluded by the `.gitignore` whitelist.

### Skills

- Each skill lives in `skills/<name>/SKILL.md` with YAML frontmatter (`name`, `description`, `argument-hint`).
- `name` must match the folder name; quote `description` values containing colons.
- Each skill is self-contained in its SKILL.md. Split a multi-step flow into separate skills and refer to them by plain name in body text (there is no `skills:` frontmatter).

### Agents

- Each agent lives in `agents/<name>.agent.md` with YAML frontmatter. Every agent has `name`, `description`, `argument-hint`, `model` (fallback list), and `agents` (dispatchable subagents); `tools`, `user-invocable`, `disable-model-invocation`, and `handoffs` are used where applicable.
- `handoffs` link user-invocable agents along meaningful transitions only and are all manual — never set `send: true`: Autopilot auto-fires the first `send` handoff after every response and can loop agents. Prompts are inserted verbatim (no `${…}` substitution) into the same session, so they name only what is handed over plus facts the target cannot see (e.g. ledger paths); the target agent's body supplies the method.
- Challenger, Examiner, and Reviewer share one verbatim `## Constraints` block and the fit question; Coder, Orchestrator, and that block share the Executor-dispatch sentence; Scout and Executor share the auto-approval bullet; Planner and Detailer share the Modules rule; Planner, Orchestrator, and Challenger share the Language rule — there is no include mechanism, so edit every copy together.

## Checks

- `make check` — Prettier format check + markdownlint.
- `make format` — auto-format all Markdown.
- Local Markdown checks and formatting (these targets or their pinned `npx` commands on specific files) may run without asking.
- CI (`.github/workflows/ci.yml`) runs `make check` on pushes to `master` and on all PRs.

## Conventions

- Agents orchestrate, skills supplement: an agent body holds its flow plus only the knowledge its role needs (Planner and Detailer design by the Modules rule; Orchestrator orchestrates; Coder implements under its test and refactoring disciplines; Reviewer, Challenger, and Examiner review; Executor and Scout run commands by their own conventions); a skill holds knowledge shared across roles and with the user (the git/gh workflow), its SKILL.md only that workflow and its commands; an agent names a skill at the step needing it rather than restating its content (deliberate exception: Coder's, Executor's, and Scout's one-line dispatched-worktree constraint, as subagents load no skill unprompted); neither restates the harness base prompt.
- Agent bodies open with one sentence in normal case, `You are the <role>: <mission>.` (Examiner, one of three in parallel, says `a <role>`) — no shouted words.
- Agent body sections are H2 only, one per name, in this order and only when needed: Input, Constraints, Approach (a subagent's checklist) or Workflow (the Orchestrator's and Planner's phase loop), Rules, Output Format.
- List items are fragments or single sentences without a terminal period — split an item rather than write two sentences in it; only Workflow phase items are paragraphs with a bold `**Phase**:` label and full punctuation, every other label is plain `Label:`.
- Emphasis: `_Agent_` italics for agent names, bold only for Workflow phase names — their labels and references back to them — and a body's key-fact line (`**Ledger**`, `**Current plan**`), backticks for paths and commands, `#tool:` for tools, skills by plain name; a list's lead-in sentence ends with a colon.
- Skills and model-invocable agents (no `disable-model-invocation: true`) carry concrete "Use when:" trigger phrases in `description` — that is the discovery surface. Every `description` is at most 35 words, shorter preferred: one outcome clause (what it does, not its steps), then `Use when:` with up to three triggers specific to the task rather than universal ones. Keep model names out of descriptions; they live in `model:` and the body.
- Keep shell snippets auto-approvable and self-contained: no `export …;` preambles or `VAR=… cmd` prefixes, no zsh-only syntax; shell variables only in steps that need approval anyway. Guards are flags, not environment: `-m`/`-F` and `--no-edit`/`--ff-only` instead of `GIT_EDITOR`, `-c core.editor=true rebase --continue`, `git --no-pager`, a flag for every value `gh` would prompt for, and a pipe (`| cat` or a filter) on `gh` output (it pages whenever the shell sets `PAGER`), watchers included rather than redirected (a redirect leaves an agent terminal silent, and 5 silent minutes move it to the background). Credential prompts need no guard: agent terminals carry VS Code's `GIT_ASKPASS` or `GIT_TERMINAL_PROMPT=0`.
- Testing policy across skills and agents: the full suite runs on CI and local runs stay targeted — the baseline from the base commit's CI run, else one local run (git-branch); tests for the change while implementing (Coder — the tests half's fail-first tests, the implementation half's and a single stage's touched tests); no full-suite requirement per commit (git-commit); every push to a PR branch runs the full suite on CI as the merge gate, its result awaited by Executor within a 30-minute default deadline, unreachable CI falling back to one local full run (pr-ci-loop); one local full run on the exact tree only before a landing that goes to no PR (finish-branch); review gates read the reviewed commit's CI result (Reviewer, Challenger).
- Execution policy across agents: only Scout (side-effect-free reads) and Executor run terminal commands, each naming its `execute/<tool>` entries instead of the `execute` set, which also carries VS Code's built-in execution subagent; Coder, Orchestrator, Reviewer, Challenger, and Examiner dispatch Executor with the worktree path, the goal or exact commands, and what to report, one dispatch per step; Executor derives a goal's commands from the repo's documented tooling and runs destructive commands only when named; the dispatcher's own constraints govern what it may ask for.
- Implementation policy across agents: the Orchestrator classifies each stage — a behavior stage as a tests/implementation pair, any other as one Coder — and records its contract and file split in the ledger before dispatch; Executor creates, joins, and lands the worktrees (git-branch, finish-branch); the halves run in parallel, each holding only its own worktree and part; the Orchestrator reads, edits, and runs nothing itself and, lacking a read tool, names skills in its dispatches; Coder is dispatch-only (`user-invocable: false`, no handoffs) and commits its verified part through Executor; the Orchestrator body is the single home of stage classification and join attribution, the Coder body of the halves' discipline (the Iron Law in pair form, good tests) and the refactoring discipline (single-stage refactorings, the joined-branch cleanup pass).
- Review policy across agents: the Orchestrator schedules review gates at Intake in every run, at least one before landing, and judges the stages between them from Executor and Scout evidence; Reviewer runs at the gates, not after every stage; Challenger runs only when the user asks (in chat or as a plan decision) or a gate fails three Reviewer rounds.
- Design policy across agents: Planner and Detailer design from the whole, by criteria that live only in the Modules rule (a change designed in rather than patched on, compatibility layers only for an explicit recorded requirement, reuse before build) and reach the plan as decisions and acceptance criteria; the Orchestrator decomposes the design; Coder implements the contract, reporting rather than writing a patch or restructuring the plan did not foresee; Reviewer, Challenger, and Examiner ask the fit question, "does this fit the plan's design or patch around it?", against those decisions and criteria.
- Planning policy across agents: complex work is planned in two layers — Planner's Outline, approved by the user before any module is detailed, then one Detailer per module of a wave, in parallel, detailing it at the functional level inside its contract; Planner and Detailer are the method's single home (the Plan, Outline, and Module Detail formats in their Output Formats); the plan states what the change is and must satisfy, never how (the Planner's Plan boundary rule); its decisions carry the landing requirement, sourced compatibility requirements, and any requested Challenger pass; the Orchestrator derives stages, gates, and landing from it and stops at an outlined wave with the Re-plan handoff; Planner alone lists Detailer in `agents`, and Detailer dispatches only Scout.
- Language policy across agents: the user-invocable agents (Planner, Orchestrator, Challenger) share one `Language:` rule — everything they write (replies, questions with their options, memory files, dispatch briefs) is in the language the user writes in, read from the user's own messages and never from a handoff prompt — so dispatched agents inherit it through their briefs and carry no rule of their own, while commits, issues, and PR text keep the project's language (git-commit, github-issue, github-pr); the harness adds a locale instruction only for a non-English VS Code display language or `github.copilot.chat.localeOverride`, so the rule restates nothing from the base prompt.
