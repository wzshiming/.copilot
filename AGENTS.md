# AGENTS.md

Personal agents repository — agent definitions plus the scripts they run, no application code.

## Structure

Only `.github/`, `agents/`, `scripts/`, `tests/`, dotfiles, root Markdown docs, `LICENSE`, and `Makefile` are tracked; everything else at the root is local runtime state excluded by the `.gitignore` whitelist.

### Scripts

- Each script lives in `scripts/<name>.sh` as POSIX sh (`#!/bin/sh`, clean under `shellcheck -s sh`), called as `~/.copilot/scripts/<name>.sh [-C <repo-path>] <args>`.
- A script never prompts, reads no environment variable as configuration, and never forces; an unmet precondition makes it refuse and say why.
- Exit codes: `0` done, `1` refused or failed, `2` usage error; a script's `--help` may define more (`ci-wait.sh`: `3` still pending at the deadline); results print as `key=value` lines, a listing (`worktree-status.sh`) as one line per item, a watcher as one progress line per poll plus the final table; `--help` prints one paragraph.
- Tests live in `tests/<name>.bats` (bats-core); reusable fake commands live in `tests/mock/<cmd>`, never as stubs written inside a single `.bats` file.

### Agents

- Each agent lives in `agents/<name>.agent.md` with YAML frontmatter. Every agent has `name`, `description`, `argument-hint`, `model` (fallback list), and `agents` (dispatchable subagents); `tools`, `user-invocable`, `disable-model-invocation`, and `handoffs` are used where applicable.
- `handoffs` link user-invocable agents along meaningful transitions only and are all manual — never set `send: true`: Autopilot auto-fires the first `send` handoff after every response and can loop agents. Prompts are inserted verbatim (no `${…}` substitution) into the same session, so they name only what is handed over plus facts the target cannot see (e.g. ledger paths); the target agent's body supplies the method.
- Challenger, Examiner, and Reviewer share one verbatim `## Constraints` block and the fit question; Coder, Orchestrator, and that block share the Executor-dispatch sentence; Scout and Executor share the auto-approval bullet; Planner and Detailer share the Modules rule; Planner, Orchestrator, and Challenger share the Language rule and the Parallel dispatch rule — there is no include mechanism, so edit every copy together.

## Checks

- `make check` — Prettier format check + markdownlint + shellcheck + bats, the full suite.
- `make lint` — markdownlint on Markdown + `shellcheck -s sh` on `scripts/*.sh`.
- `make test` — bats-core on `tests/*.bats`.
- `make format` — Prettier rewrites Markdown.
- These targets, or the commands they run on specific files, may run locally without asking.
- CI (`.github/workflows/ci.yml`) runs `make check` on `ubuntu-latest` and `macos-latest` for pushes to `master` and all PRs.

## Conventions

- Agents orchestrate, Executor executes: an agent body holds its flow plus only the knowledge its role needs (Planner and Detailer design by the Modules rule; Orchestrator orchestrates; Coder implements under its test and refactoring disciplines; Reviewer, Challenger, and Examiner review; Executor and Scout run commands by their own conventions); the git/gh workflow lives only in Executor's Rules, and each fixed multi-command flow is a script in `scripts/` that Executor names at the rule needing it; dispatchers (Orchestrator, Coder, Reviewer, Challenger, Examiner) ask for a git/gh step by its intent alone — create a worktree, commit, land, wait on CI, read a commit's CI result, clean up a worktree, open an Issue — never by a command form or another document, the one exception being Coder's exact `git add <paths>` and `git commit` commands for its own files (its Commit step); Coder, Scout, and Executor each keep a one-line restatement of the dispatched-worktree constraint, as a subagent is stateless and receives only its body and brief; no body restates the harness base prompt.
- Agent bodies open with one sentence in normal case, `You are the <role>: <mission>.` (Examiner, one of three in parallel, says `a <role>`) — no shouted words.
- Agent body sections are H2 only, one per name, in this order and only when needed: Input, Constraints, Approach (a subagent's checklist) or Workflow (the Orchestrator's and Planner's phase loop), Rules, Output Format.
- List items are fragments or single sentences without a terminal period — split an item rather than write two sentences in it; only Workflow phase items are paragraphs with a bold `**Phase**:` label and full punctuation, every other label is plain `Label:`.
- Emphasis: `_Agent_` italics for agent names, bold only for Workflow phase names — their labels and references back to them — and a body's key-fact line (`**Ledger**`, `**Current plan**`), backticks for paths and commands, `#tool:` for tools; a list's lead-in sentence ends with a colon.
- Model-invocable agents (no `disable-model-invocation: true`) carry concrete "Use when:" trigger phrases in `description` — that is the discovery surface. Every `description` is at most 35 words, shorter preferred: one outcome clause (what it does, not its steps), then `Use when:` with up to three triggers specific to the task rather than universal ones. Keep model names out of descriptions; they live in `model:` and the body.
- Keep shell snippets auto-approvable and self-contained: a fixed flow is one script call, approvable whole; any other command has no `export …;` preamble or `VAR=… cmd` prefix and no zsh-only syntax, with shell variables only in steps that need approval anyway. Guards are flags, not environment: `-m`/`-F` and `--no-edit`/`--ff-only` instead of `GIT_EDITOR`, `-c core.editor=true rebase --continue`, `git --no-pager`, a flag for every value `gh` would prompt for, and a pipe (`| cat` or a filter) on `gh` output (it pages whenever the shell sets `PAGER`), watchers included rather than redirected (a redirect leaves an agent terminal silent, and 5 silent minutes move it to the background). Credential prompts need no guard: agent terminals carry VS Code's `GIT_ASKPASS` or `GIT_TERMINAL_PROMPT=0`.
- Testing policy across agents and scripts: the full suite runs on CI and local runs stay targeted — the baseline from the base commit's CI run, else one local run (Executor's Worktree rule); tests for the change while implementing (Coder — the tests half's fail-first tests, the implementation half's and a single stage's touched tests); no full-suite requirement per commit (Coder's Commit step); every push to a PR branch runs the full suite on CI as the merge gate, its result awaited by Executor within a default deadline, unreachable CI falling back to one local full run (Executor's CI rule and `scripts/ci-wait.sh`); one local full run on the exact tree only before a landing that goes to no PR (Executor's Landing rule); review gates read the reviewed commit's CI result (Reviewer, Challenger).
- Execution policy across agents: only Scout (side-effect-free reads) and Executor run terminal commands, each naming its `execute/<tool>` entries instead of the `execute` set, which also carries VS Code's built-in execution subagent; Coder, Orchestrator, Reviewer, Challenger, and Examiner dispatch Executor with the worktree path, the goal or exact commands, and what to report, one dispatch per step; Executor derives a goal's commands from the repo's documented tooling and runs destructive commands only when named; the dispatcher's own constraints govern what it may ask for.
- Implementation policy across agents: the Orchestrator classifies each stage — a behavior stage as a tests/implementation pair, any other as one Coder — and records its contract and file split in the ledger before dispatch; Executor creates, joins, and lands the worktrees (Executor's Worktree and Landing rules with `scripts/worktree-*.sh`); the halves run in parallel, each holding only its own worktree and part; the Orchestrator reads, edits, and runs nothing itself; Coder is dispatch-only (`user-invocable: false`, no handoffs) and commits its verified part through Executor; the Orchestrator body is the single home of stage classification and join attribution, the Coder body of the halves' discipline (the Iron Law in pair form, good tests) and the refactoring discipline (single-stage refactorings, the joined-branch cleanup pass).
- Review policy across agents: the Orchestrator schedules review gates at Intake in every run, at least one before landing, and judges the stages between them from Executor and Scout evidence; Reviewer runs at the gates, not after every stage; Challenger runs only when the user asks (in chat or as a plan decision) or a gate fails three Reviewer rounds.
- Design policy across agents: Planner and Detailer design from the whole, by criteria that live only in the Modules rule (a change designed in rather than patched on, compatibility layers only for an explicit recorded requirement, reuse before build) and reach the plan as decisions and acceptance criteria; the Orchestrator decomposes the design; Coder implements the contract, reporting rather than writing a patch or restructuring the plan did not foresee; Reviewer, Challenger, and Examiner ask the fit question, "does this fit the plan's design or patch around it?", against those decisions and criteria.
- Planning policy across agents: complex work is planned in two layers — Planner's Outline, approved by the user before any module is detailed, then the Detailers of a wave together in one tool-call block, each detailing its module at the functional level inside its contract, a wave being every outlined module that needs no code still unlanded; Planner and Detailer are the method's single home (the Plan, Outline, and Module Detail formats in their Output Formats); the plan states what the change is and must satisfy, never how (the Planner's Plan boundary rule); its decisions carry the landing requirement, sourced compatibility requirements, and any requested Challenger pass; the Orchestrator derives stages, gates, and landing from it, orders a wave's stages by the modules' declared dependencies, and stops at an outlined wave with the Re-plan handoff; Planner alone lists Detailer in `agents`, and Detailer dispatches only Scout.
- Dispatch policy across agents: subagent dispatches needing none of one another's results or side effects form one batch issued in one tool-call block, because the harness runs concurrently only the calls of one block and a dispatch issued after another has returned runs alone; each body names its batches — Planner's Discovery Scouts and the Detailers of a wave, the Orchestrator's Intake Scouts, the two halves of a pair, and singles with no declared dependency and disjoint files, Challenger's three Examiners — and the rule's single home is the shared `Parallel dispatch:` Rules bullet of the three user-invocable agents (Planner, Orchestrator, Challenger); the harness base prompt asks only generically for independent calls in one block, and the rule adds what counts as a batch here and that a later dispatch runs alone, so it restates nothing from the base prompt.
- Language policy across agents: the user-invocable agents (Planner, Orchestrator, Challenger) share one `Language:` rule — replies and questions (options included) are in the language the user writes in, read from the user's own messages and never from a handoff prompt — and nothing else (dispatch briefs, subagent reports, memory files) is bound to it, so the dispatch-only agents carry no rule of their own, while commits, issues, and PR text keep the project's language (Coder's Commit step and Executor's PR and Issue rules); the harness adds a locale instruction only for a non-English VS Code display language or `github.copilot.chat.localeOverride`, so the rule restates nothing from the base prompt.
